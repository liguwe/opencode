# opencode 工程目录概览

这份文档只解决一个问题：先从目录结构上看清 `opencode` 这个工程大概怎么组织。

`opencode` 是一个 Bun + TypeScript monorepo。它不是单一 CLI 包，而是一组围绕 AI Coding Agent 的产品包。

**核心产品矩阵：**

- CLI/TUI 运行时 → 终端里直接交互
- 核心状态与数据库 → SQLite 持久化 + Effect 层
- 模型 Provider → 多模型适配（Anthropic、OpenAI、Google、Bedrock 等）
- Web/桌面/App UI → Solid、Electron、Astro
- SDK → 外部集成接口
- 插件 → 可扩展的 tool/skill/command 体系
- 外围产品 → 企业版、Slack 集成、统计

```text
opencode/
|-- package.json             # Bun workspace + Turbo 任务入口
|-- bun.lock                 # Bun 锁文件

|-- tsconfig.json            # 根 TypeScript 配置
|-- README.md                # 当前保留的中文 README
|-- AGENTS.md                # Agent 协作规则
|
|-- packages/                # 主 workspace，核心代码都在这里
|-- sdks/                    # 外部 SDK，例如 VSCode
|-- specs/                   # 协议/存储规格
|-- script/                  # repo 级脚本
|-- github/                  # GitHub 自动化相关包
|-- infra/                   # 基础设施配置
|-- nix/                     # Nix 相关配置
|-- patches/                 # Bun patchedDependencies 补丁
|-- perf/                    # 性能实验/记录
|
|-- .opencode/               # 本仓库自己的 opencode 配置、agent、skill、plugin
|-- .github/                 # GitHub workflow/action/issue template
|-- .husky/                  # Git hook
|-- .vscode/ .zed/           # 编辑器配置
```

顶层 `package.json` 说明这个工程的基本技术栈：

```text
运行时
  Bun 1.3.x
    ├── workspaces: packages/*
    ├── workspaces: packages/console/*
    ├── workspaces: packages/stats/*
    ├── workspaces: packages/sdk/js
    └── workspaces: packages/slack

构建
  Turbo
    ├── typecheck ─── 全量类型检查
    ├── build ─────── 打包构建
    └── package-level tasks ─── 各包自定义脚本

核心依赖
  TypeScript
    ├── Effect ─────── 函数式 effect 系统，贯穿全局
    ├── Hono ───────── HTTP 服务框架
    ├── Solid ──────── 前端 UI 框架（Web + TUI）
    ├── OpenTUI ────── 终端 UI 组件库
    ├── AI SDK ─────── LLM 调用抽象（Vercel AI SDK）
    └── Drizzle/SQLite ─ 数据库 ORM + 本地存储

关键设计决策
  - Effect 作为核心抽象：错误处理、依赖注入、资源管理都用 Effect
  - SQLite 本地优先：session/message/project 都在本地 sqlite
  - Bun 为唯一运行时：不兼容 Node
  - monorepo 不拆多仓库：产品面、核心、SDK 共处一个 workspace
```

## Session / Agent Loop 大致位置

关键目录：

```text
src/session/
|-- session.ts             # session 信息、创建/恢复/分叉/持久化
|-- message.ts             # message 模型
|-- message-v2.ts          # v2 message 模型
|-- prompt.ts              # prompt 组装
|-- processor.ts           # session 处理流程
|-- llm.ts                 # LLM 调用入口
|-- llm/                   # AI SDK/native request/runtime
|-- tools.ts               # session 可用工具
|-- compaction.ts          # 上下文压缩
|-- overflow.ts            # token overflow 处理
|-- summary.ts             # session summary
|-- todo.ts                # todo 状态
|-- system.ts              # system prompt 相关
`-- prompt/*.txt           # 不同模型/agent 的提示词模板
```

可以先把 Agent Loop 理解成：

```text
user input
  |
  v
Session prompt builder
  |
  +-- project instructions
  +-- agent prompt
  +-- model-specific prompt
  +-- previous messages
  +-- tool definitions
  |
  v
LLM request
  |
  v
model response stream
  |
  +-- assistant text
  +-- tool call
  +-- reasoning/status
  |
  v
tool execution / permission
  |
  v
append message parts
  |
  v
continue until idle / stop
```

这部分和 Codex Rust 里的 `Agent Loop + Thread/Session + Tool Call` 是同一类问题，只是 opencode 用 TypeScript、Effect、AI SDK、SQLite 来组织。

#### Agent Loop 关键类型（概念层）

```text
Session
  ├── id / project / title
  ├── messages: Message[]
  ├── status: idle | running | stopped
  └── metadata

Message
  ├── role: user | assistant | system | tool
  ├── content: Part[]（多模态 parts）
  ├── parentId（消息链）
  └── timestamp / metadata

Message Part
  ├── text
  ├── tool_call（工具调用请求）
  ├── tool_result（工具执行结果）
  └── reasoning（思考过程）

Prompt Builder
  ├── project instructions ─── 项目级 .opencode/agent/*.md
  ├── agent prompt ────────── 内置 agent 定义
  ├── model-specific prompt ── 不同模型的格式适配
  ├── system prompt ───────── 系统指令
  ├── tool definitions ────── 可用工具 JSON Schema 列表
  └── previous messages ───── 历史消息（受 context window 限制）
```

#### Session 生命周期

```text
创建 ──► 运行 ──► 空闲 ──► 恢复/分叉/归档
  │                │
  │                ├── compaction（上下文压缩）
  │                ├── summary（生成摘要）
  │                ├── overflow（token 超限处理）
  │                └── todo（跟踪待办）
  │
  └── 持久化到 SQLite（每步都写）
```

src/tool/
|-- read.ts / read.txt
|-- write.ts / write.txt
|-- edit.ts / edit.txt
|-- apply_patch.ts / apply_patch.txt
|-- shell.ts
|-- grep.ts / glob.ts
|-- webfetch.ts / websearch.ts
|-- task.ts / skill.ts
|-- todo.ts / question.ts
|-- lsp.ts
|-- repo_clone.ts / repo_overview.ts
`-- registry.ts
```

注册流程大致是：

```text
ToolRegistry.layer
  |
  +-- load builtin tools
  |     |
  |     +-- ShellTool
  |     +-- ReadTool
  |     +-- EditTool
  |     +-- ApplyPatchTool
  |     +-- GrepTool / GlobTool
  |     +-- WebFetchTool / WebSearchTool
  |     +-- TaskTool / SkillTool
  |     `-- ...
  |
  +-- scan config directories
  |     |
  |     `-- {tool,tools}/*.{js,ts}
  |
  +-- load plugin tools
  |
  +-- normalize schema
  |
  `-- expose tools(model, agent)
```

工具系统的关键点：

```text
LLM-visible tool schema
  |
  v
Tool.Def
  ├── id ──────────── 唯一标识
  ├── description ─── LLM 看到的工具描述
  ├── parameters ──── JSON Schema 参数定义
  └── execute(args, toolCtx)
         ├── permission check ── 权限评估
         ├── file/shell/network ── 实际操作
         ├── output truncation ── 大输出截断
         └── return ToolResult ── 返回给 LLM
```

#### 工具上下文 (ToolCtx)

```text
ToolCtx
  ├── session ────── 当前 session 引用
  ├── project ────── 项目信息
  ├── signal ─────── 取消信号
  ├── outputLimit ── 输出长度限制
  └── hooks ──────── 钩子（before/after）
```

#### 关键设计点

- 每个工具都有一个 `.txt` 文件定义其 LLM prompt 描述
- 工具通过 `ToolRegistry.layer` 分层加载：内置 → 配置目录 → 插件
- 工具 schema 会被合并到每次 LLM 请求的 tool definitions 中
- shell 工具是整个系统中最强大但也最危险的工具

## Permission / Sandbox

关键目录：

```text
src/permission/
|-- index.ts
|-- evaluate.ts
`-- arity.ts
```

opencode 的权限模型不像 Codex Rust 那样首先从 OS sandbox 视角切入；它更像在工具执行前做一层策略评估和交互确认：

```text
tool wants action
  |
  v
Permission.evaluate(...)
  |
  +-- allow
  +-- ask
  `-- deny
        |
        v
TUI footer.permission / question
        |
        v
user decision
        |
        v
continue tool execution or stop
```

`opencode run --dangerously-skip-permissions` 这类参数也在 `run.ts` 里出现，说明权限策略和运行模式强相关。

#### 权限策略类型

```text
Permission Policy
  ├── allow ──────── 直接放行
  ├── deny ───────── 直接拒绝
  ├── ask ────────── 弹出交互确认
  └── ask_always ─── 每次都确认，不记住
```

#### Permission 评估输入

```text
evaluate(params)
  ├── tool id ────────── 哪个工具
  ├── action ─────────── 具体操作（如 "write file"）
  ├── params ─────────── 工具参数
  ├── session ────────── 当前会话
  └── previous decisions ─ 历史决策（allow/deny 的记忆）

```text

  ├── model: "claude-sonnet-4-6"

#### 支持的 Provider 全家福

```text

## .opencode 目录

这个仓库自己也带了一套 opencode 配置：

```text
.opencode/
|-- agent/
|-- command/
|-- glossary/
|-- plugins/
|-- skills/
|-- themes/
`-- tool/
```

这说明 opencode 不只是”一个 CLI”，它也把 agent、command、skill、tool、theme 当作可配置/可扩展资源。这一点对 General Agent Product 很关键：产品能力不是都写死在 runtime 里，而是通过配置目录暴露扩展点。

#### 扩展体系

```text
.opencode/
  ├── agent/    ─── 自定义 agent 定义（prompt + tool scope）
  ├── command/  ─── 自定义 slash 命令
  ├── glossary/ ─── 项目术语表
  ├── plugins/  ─── 插件（npm 包 / 本地）
  ├── skills/   ─── skill 定义（可复用的能力片段）
  ├── themes/   ─── 终端主题自定义
  └── tool/     ─── 自定义工具（.js/.ts）
```

#### 扩展加载方式

```text
配置目录扫描
  ├── 全局 ~/.config/opencode/
  ├── 项目 .opencode/
  └── 插件 node_modules 中的 .opencode/

加载优先级
  项目级 > 插件级 > 全局级 > 内置
```

## 和 Codex CLI 的第一层对照

```text
Codex CLI
  |
  +-- codex-cli/          npm wrapper, very thin
  +-- codex-rs/           Rust native CLI/TUI/agent core

opencode
  |
  +-- packages/opencode/  TS/Bun CLI/TUI/agent core
  +-- packages/core/      shared state/database/model foundation
  +-- packages/llm/       provider/protocol abstraction
  +-- packages/app/web/desktop/ui
```

最明显的差异：

```text
Codex:
  npm wrapper -> Rust native binary -> CLI/TUI/Agent

opencode:
  Bun package -> TypeScript runtime -> CLI/TUI/Server/Agent
```

### 逐项对照

```text
维度              Codex                         opencode
────────────────  ───────────────────────────  ─────────────────────────
语言               Rust                          TypeScript (Bun)
Agent 运行时        codex-rs (Rust native)        packages/opencode (TS)
CLI 入口            npm wrapper (JS)              packages/opencode/bin/opencode
LLM 适配            Rust native HTTP client       @opencode-ai/llm (多协议)
数据库              SQLite (libsql)               SQLite (Drizzle + Effect)
工具系统            内置 + MCP                    内置 + 配置 + 插件 + MCP
终端 UI             Rust TUI (ratatui)            OpenTUI + Solid
权限模型            OS sandbox 视角                策略评估 + 交互确认
插件体系            MCP 协议                      自定义 plugin API + MCP
产品面              CLI/TUI only                  CLI + TUI + Web + Desktop + SDK
包管理              npm workspace                 Bun workspace + Turbo
```

opencode 的 monorepo 更像一个完整产品工程：CLI、TUI、Web、Desktop、SDK、插件、Provider、数据库和云端/企业能力都在一个 workspace 里。读源码时不要只看 `packages/opencode`，但第一阶段应该以它为主线，再向 `core`、`llm`、`app` 展开。

### 从 Codex 视角看 opencode 的亮点

```text
1. Effect 贯穿全局
   - 错误处理不再是 try/catch，而是 Effect 的 error channel
   - 依赖注入不用传参，通过 Effect Context
   - 资源生命周期管理（如 DB 连接）天然安全

2. 多产品面共用 Agent Runtime
   - CLI/TUI、Web App、Desktop 都通过同一个 server + SDK
   - 不需要为每个产品面重写 Agent 逻辑

3. 配置驱动的扩展体系
   - .opencode/ 目录下的 agent/command/skill/tool/theme 全部可自定义
   - 插件可以是一个 npm 包，自带 .opencode/ 配置

4. TypeScript 可读性
   - 对于前端/全栈背景，TypeScript 源码比 Rust 更容易上手
   - 类型系统提供了足够的自文档化
```

### 阅读时关注的核心问题

```text
每个文件阅读时带着这些问题：

1. CLI 入口

   - Stream 如何处理 tool call 的增量？

5. Tool
   - 工具如何注册？
   - 执行前权限检查在哪一步？
